# ESPBridge

Прозрачный мост UART ↔ Ethernet на двух платах WT32-ETH01.

Пробрасывает два независимых UART-потока через IP-сеть: канал управления
(CRSF) и телеметрию (MAVLink). Наземный модуль принимает данные с пульта и
отправляет по UDP, бортовой принимает из сети и выдаёт в полётный контроллер.

```
 [пульт] --UART--> [ESP32 GROUND] --UDP--> [ESP32 AIR] --UART--> [FC]
                    192.168.4.1              192.168.4.2
```

Фреймворк — **ESP-IDF 6.x**.

## Состояние

| Что | Статус |
|---|---|
| Ethernet, статический IP | собирается; на Arduino-версии линк поднимался на железе |
| Одна прошивка на обе платы, роль в настройках | собирается, на железе не проверено |
| Прозрачный режим UART ↔ UDP | собирается, на железе не проверено |
| CRSF: разбор фреймов и выдача по таймеру | собирается, на железе не проверено |
| Прошивка по сети (OTA) | собирается, на железе не проверено |
| Веб-интерфейс, настройка IP | собирается, на железе не проверено |
| Консоль и дамп трафика на UART0 | собирается, на железе не проверено |
| S-Port (инверсия, half-duplex) | не сделано |
| Обратный канал телеметрии | не сделано |
| Шифрование | не сделано |

## Железо

**WT32-ETH01** — ESP32-WROOM-32 + LAN8720A по RMII, RJ45 на плате.

Интерфейс RMII занимает большую часть GPIO, наружу выведено немного, и часть
выведенных пинов работает только на вход. Отсюда распиновка:

| Порт | Назначение | TX | RX | UDP |
|---|---|---|---|---|
| Порт 0 | CRSF | GPIO32 | GPIO33 | 14551 |
| Порт 1 | MAVLink | GPIO14 | GPIO15 | 14550 |
| UART0 | прошивка и лог | TXD0 | RXD0 | — |
| — | индикация | GPIO2 | | |

Пины и UDP-порты — значения по умолчанию, **меняются через веб-интерфейс**
и применяются после перезагрузки. У каждого порта задаются отдельно порт
приёма и порт отправки: обычно они совпадают, но наземная станция может
ждать данные на своём — например, QGroundControl на 14550.

GPIO32/33 отданы под CRSF как свободные от strapping-функций — этот канал
чувствителен к таймингу.

Что стоит знать о доступных пинах WT32-ETH01:

| Пин | Особенность |
|---|---|
| 4, 32, 33 | чистые |
| 14 | выдаёт PWM в момент загрузки |
| 15 | при высоком уровне на старте выводится загрузочный лог |
| 2 | мешает входу в режим прошивки при высоком уровне |
| 5, 17 | на линии светодиод — искажает фронты сигнала |
| 12 | плата не загрузится, если при старте высокий уровень |
| 35, 36, 39 | только вход, под TX не годятся |
| 0, 16, 18, 19, 21–23, 25–27 | заняты интерфейсом Ethernet |
| 1, 3 | UART0, прошивка и лог |

UART на ESP32 не привязан к конкретным ножкам: сигналы любого из трёх
аппаратных контроллеров разводятся на почти любой GPIO через матрицу
коммутации. Пины по умолчанию (16/17 для UART2) на этой плате недоступны —
GPIO16 занят питанием PHY, GPIO17 нагружен светодиодом.

UART0 оставлен под прошивку и отладочный лог, а не под данные.

**Питание только 5 В.** От 3.3 В плата стартует, но LAN8720 не поднимается —
самая частая причина «лог есть, линка нет».

Уровни UART — 3.3 В. Если полётный контроллер отдаёт 5 В, на линию RX нужен
делитель.

## Сборка

Нужен [PlatformIO Core](https://platformio.org/install/cli):

```
pip install platformio
```

```
pio run
```

Первая сборка скачивает ESP-IDF и toolchain — несколько сотен мегабайт.

**Прошивка одна для обеих плат.** Роль (GROUND/AIR) и адреса задаются через
веб-интерфейс и хранятся в NVS, поэтому перепутать образы при заливке
невозможно.

## Прошивка

> **Заливать нужно `*_MERGED.bin`, а не `firmware.bin`.**
>
> `pio run` создаёт `firmware.bin` — только прошивку, без загрузчика и
> таблицы разделов. Залитая по адресу `0x0`, она не запустится: плата не
> найдёт заголовок и уйдёт в бесконечную перезагрузку с сообщением
> `invalid header: 0x...` и `rst:0x10 (RTCWDT_RTC_RESET)`.
>
> Единый образ `*_MERGED.bin` содержит загрузчик, таблицу разделов и
> прошивку, каждое по своему адресу.

### Сборка образа

```
./build.sh
```

Результат — `out/espbridge_MERGED.bin`. Скрипт проверяет, что образ собрался
корректно.

### Заливка

```
esptool --chip esp32 --port COM15 --baud 921600 write-flash -z \
  --flash-mode dio --flash-freq 80m --flash-size 4MB \
  0x0 out/ground_MERGED.bin
```

В Linux порт указывается как `/dev/ttyUSB0`.

Если плата до этого была прошита неудачно, сначала стереть флеш:

```
esptool --chip esp32 --port COM15 erase-flash
```

### Вручную

Если нужно собрать образ без скриптов:

```
pio run -e ground

esptool --chip esp32 merge-bin -o ground.bin \
  --flash-mode dio --flash-freq 80m --flash-size 8MB \
  0x1000  .pio/build/ground/bootloader.bin \
  0x8000  .pio/build/ground/partitions.bin \
  0xe000  ~/.platformio/packages/framework-arduinoespressif32/tools/partitions/boot_app0.bin \
  0x10000 .pio/build/ground/firmware.bin

esptool --chip esp32 --port COM15 --baud 921600 write-flash -z \
  --flash-mode dio --flash-freq 80m --flash-size 8MB 0x0 ground.bin
```

WT32-ETH01 не имеет USB — нужен переходник USB–UART на 3.3 В (RX0↔TX,
TX0↔RX, GND). Для входа в режим прошивки замкнуть **IO0 на GND**, подать
питание, залить, снять перемычку, перезапустить.

## Прошивка по сети (OTA)

После того как плата хотя бы раз прошита по проводу и доступна по своему
адресу, обновлять можно без кабеля — двумя способами.

### Через браузер

На странице настроек, раздел «Обновление прошивки»: выбрать файл, нажать
«Прошить», дождаться прогресса, перезагрузить.

Нужен **`firmware.bin`** из `.pio/build/espbridge/`, а не
`espbridge_MERGED.bin`. По сети обновляется только раздел приложения;
загрузчик и таблица разделов остаются на месте, и склеенный образ здесь
не подойдёт — плата его отвергнет с ошибкой проверки.

### Через PlatformIO

```
pio run -e ota -t upload
```

Адрес прошиваемой платы указывается в `upload_port` в `platformio.ini`,
пароль — в `upload_flags`.

Пароль — `espbridge`, задан в `main/config.h` и продублирован в
`platformio.ini`. Без пароля любой в сети мог бы залить свою прошивку.

Запись идёт в неактивный раздел: таблица разделов содержит два раздела
приложения по 1.5 МБ. Загрузчик переключается на новый только после того,
как образ записан целиком и прошёл проверку контрольной суммы. Обрыв связи
посреди записи не выводит плату из строя — она продолжит грузиться со
старого раздела.

На время записи мост останавливается: обслуживание портов отнимает время
у записи во flash.

## Настройка

### Веб-интерфейс

`http://192.168.4.1/` и `http://192.168.4.2/`. Компьютеру задать адрес
в той же подсети, например `192.168.4.100`, маска `255.255.255.0`.

Меняются: IP модуля, маска, шлюз, адрес партнёра, скорость и режим каждого
порта, частота выдачи CRSF. Там же — живые счётчики.

Параметры портов применяются сразу. **Сетевые — только после перезагрузки**:
смена адреса на лету оборвала бы соединение, через которое пришла команда,
до отправки ответа.

Настройки хранятся в NVS. Кнопка «Сбросить настройки» возвращает значения
по умолчанию для роли, заданной при сборке.

### Консоль на UART0

Работает без сети — это важно, когда сеть как раз и не поднимается.
Подключиться монитором на 115200 и ввести `help`.

```
stat              счётчики портов
dbg <флаги>       traffic hex crsf pacer net timing all off
mode <0|1> <t|c>  прозрачный или CRSF
baud <0|1> <bps>  скорость
pps <0|1> <Гц>    частота выдачи CRSF
reboot
```

Команда `dbg hex` включает дамп содержимого пакетов — в hex и печатными
символами одновременно:

```
dbg 1 port0 UART->сеть 26 Б | c8 18 16 e0 03 1f | ......
```

Частота дампа ограничена 200 мс и 32 байтами: на 400 кбод печать каждого
пакета сделала бы лог узким местом и исказила измеряемые тайминги.

Команда `dbg timing` печатает раз в секунду период выдачи CRSF, минимум,
максимум и разброс — прямая проверка работы выравнивателя темпа.

## Режимы работы

**Прозрачный** — байты идут через мост как есть, без разбора. Подходит для
MAVLink и любого потокового протокола.

Байты не отправляются поодиночке: 40+ байт заголовков на один байт данных
захлебнули бы сеть. Приёмный буфер копится до 500 мкс или до заполнения,
после чего уходит одной датаграммой. При 400 кбод это около 20 байт — примерно
один CRSF-фрейм.

**CRSF** — поток разбирается на фреймы с проверкой CRC8, фреймы кладутся в
очередь и выдаются в UART собственным таймером на заданной частоте (25–250 Гц,
по умолчанию 150).

Прозрачный проброс CRSF в полётный контроллер не работает: UDP доставляет
пакеты пачками и с джиттером, а Betaflight/INAV ждут равномерного потока и при
срыве темпа поднимают failsafe. Выравнивание темпа — не оптимизация, а условие
работоспособности.

При переполнении очереди выбрасываются **старые** фреймы: для управления
свежая команда ценнее устаревшей.

## Структура

```
main/
  main.c          запуск, задачи индикации и отчёта
  config.h        распиновка, адреса, размеры буферов
  net_eth.c       подъём LAN8720, статический IP
  port.c          UART ↔ UDP, задачи обоих направлений
  crsf.c          разбор потока на фреймы, CRC8
  crsf_pacer.c    очередь и выдача по таймеру
sdkconfig.defaults  настройки ESP-IDF
```

Каждый порт обслуживают три задачи FreeRTOS: приём с UART, приём из сети и
выдача по таймеру. Приём с UART имеет более высокий приоритет — пропущенные
байты на линии не восстановить, а сетевой пакет подождёт в буфере стека.

Выдача в режиме CRSF идёт по аппаратному таймеру `esp_timer` с микросекундной
точностью. Планировщик FreeRTOS для этого не годится: даже при тике 1 мс
период 6.67 мс (150 Гц) округлится до 6 или 7 мс, то есть до 166 или 143 Гц.

## Диагностика

Раз в пять секунд прошивка печатает в лог счётчики по каждому порту:
принято и передано в UART, отправлено и принято по UDP, состояние партнёра.

```
I (5234) main: port0: UART rx=1024 tx=980 | UDP tx=52 rx=49 | партнёр на связи
```

По ним видно, на каком участке обрыв: не читается UART, не уходит UDP,
не приходит UDP или не пишется в UART.

Светодиод GPIO2: редкое мигание — линка нет, частое — линк есть но партнёр
молчит, горит ровно — идёт обмен.
